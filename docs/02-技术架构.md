## 二、技术选型

### 核心语言
| 组件 | 语言 | 理由 |
|------|------|------|
| 数据采集脚本 | Python 3.13 | 生态最丰富（feedparser/requests/beautifulsoup4） |
| 报告生成 | Python + Jinja2 | 模板渲染成熟 |
| 前端（HTML报告） | 纯HTML/CSS/JS（无框架） | 零依赖，加载快，维护简单 |
| 数据可视化 | Chart.js（CDN） | 轻量，移动端友好 |

### 关键依赖库（Python）
| 库 | 用途 |
|------|------|
| `feedparser` | RSS解析 |
| `requests` + `httpx` | HTTP请求 |
| `beautifulsoup4` + `lxml` | 网页解析 |
| `jinja2` | HTML模板渲染 |
| `markdown` | 内容转换 |

### 运行环境
- Python 3.13（managed version，隔离环境）
- 所有依赖安装在项目 venv 中

## 三、数据流设计

```
7:00  采集启动
      ├── RSS源并行抓取（~30s）
      ├── API源并行调用（~20s）
      └── 爬虫源顺序抓取（~3min）
      
7:05  数据处理
      ├── 去重（基于标题/URL/内容相似度）
      ├── 版块分类（基于关键词+AI语义分类）
      ├── 关键信息提取（保留原文段落）
      └── 准IPO数据补充（企查查API）

7:15  AI处理
      ├── 摘要生成（每版块200-500字导读）
      ├── 交叉验证标注
      └── 每日寓言生成

7:25  报告生成
      ├── HTML模板渲染
      ├── 数据图表嵌入
      └── 移动端适配检查

7:30  部署推送
      ├── CloudStudio部署（~1min）
      ├── 飞书消息推送
      └── 生成状态日志

8:00  用户收到推送
```

## 五、容错设计

| 环节 | 容错策略 |
|------|------|
| 单个信源失败 | 标记失败，继续采集其他源，不阻塞整体流程 |
| 爬虫页面结构变更 | 异常捕获 + 降级策略（用RSS源替代） |
| AI处理超时 | 降级为基础关键词分类 |
| 部署失败 | 本地保留HTML，下次采集时重试部署 |
| 推送失败 | 日志记录，次日手动推送 |

报告中始终包含「信源状态」版块，标注哪些信源正常、哪些降级、哪些失败。

## 六、安全边界

- 所有采集仅访问公开信息
- 不存储任何个人数据
- API Key 存储在本地配置文件，不入版本控制
- HTML报告零cookie、零tracking
